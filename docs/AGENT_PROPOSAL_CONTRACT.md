# Agent proposal contract

The Agent contract exists to make delegated editing inspectable, reversible, and compatible with the same project mutation boundary as direct manipulation.

## Core modules

- `packages/core/src/agent-plan.js` — proposal schema, graph binding, preflight, revision, operation selection, approval transaction.
- `packages/core/src/agent-review.js` — bounded human-readable review model.
- `packages/core/src/agent-rebase.js` — explicit safe rebase across known intervening transactions.
- `packages/core/src/providers.js` — planner provider boundary, context filtering, result bounds, model-router planner bridge.
- `apps/studio/agent-proposal-session.js` — Studio-facing pending proposal lifecycle.

## Proposal invariants

Every `media.agent-plan.v1` proposal is bound to:

- a project id;
- a semantic fingerprint of the graph it was planned against;
- a preview fingerprint produced by applying its operations;
- a provider identity;
- intent, summary, revision, and JSON-safe bounded metadata;
- a validated operation list.

Proposal creation applies the complete operation list to the current graph in memory. If graph invariants fail, the proposal is rejected before it can be shown as valid work.

## Stale plans

A plan is stale whenever the current semantic graph fingerprint differs from its base fingerprint.

A stale plan must not be silently applied.

The caller may:

- discard it;
- ask the provider to plan again;
- explicitly rebase it by supplying the exact intervening transactions.

`rebaseAgentPlan` uses the existing operation-conflict resource model. A rebase is accepted only if the intervening transactions reconstruct the current graph exactly and none conflict with the proposal operations.

## Human revision

Operation-level selection creates a new proposal revision. Selection is not a UI-only filter: the selected operation subset is re-applied and preflighted as a complete batch.

This matters for dependent edits. For example, retaining an edge creation while dropping the node creation it depends on is rejected instead of producing a broken project.

## Review model

`createAgentPlanReview` returns:

- plan/revision/provider identity;
- base and preview fingerprints;
- operation counts and affected node/edge identities;
- one bounded review entry per operation;
- before/after summaries for updates.

Large arrays, objects, and strings are summarized so review itself cannot accidentally materialize enormous media/project payloads.

## Approval

Approval converts the plan into a normal graph transaction. The transaction metadata includes:

- `source: "agent"`;
- Agent plan schema/id/revision;
- provider id;
- original intent;
- base and preview fingerprints.

Consumers should commit those operations through the normal durable journal boundary. Do not apply the preview graph directly as a side channel.

## Studio session behavior

`AgentProposalSession` deliberately keeps one pending plan.

- `propose()` replaces the pending plan with a freshly preflighted proposal.
- `snapshot()` reports `idle`, `pending`, or `stale`.
- `select()` creates a new plan revision.
- `apply()` commits the approved transaction and clears pending state only after the commit succeeds.
- `discard()` clears pending state without mutation.

If durable persistence fails, the pending plan remains available for retry or discard. That prevents UI state from pretending an Agent edit succeeded when the journal/storage transaction did not.

## Provider boundary

Planner providers are untrusted inputs even when invoked locally.

Current bounds include:

- maximum operation count;
- maximum summary length;
- maximum canonical result bytes;
- maximum HTTP request bytes;
- maximum declared/streamed HTTP response bytes.

Remote graph snapshots strip local asset URIs/waveforms and enforce Creative Object model-access policy.

The Model Router planner bridge additionally records which backend actually produced a routed proposal and which semantic matches were used for focused context.

## Generated media relationship

An Agent plan may lead to generative model execution, but the generated binary is not itself an Agent operation payload.

`generation-runner.js` executes the model with privacy-filtered source context and returns:

- ephemeral binary/model payload;
- a normal generated-asset descriptor;
- a bounded generation record;
- ordinary graph operations that materialize the asset and relationships.

The storage layer should persist generated bytes and graph/journal changes atomically when that workflow is wired into Studio.

## Non-goals

The Agent proposal contract does not:

- define a particular model vendor;
- make model output authoritative;
- bypass graph invariants;
- bypass history/journaling;
- automatically rebase ambiguous changes;
- store large model/media payloads in operation metadata;
- silently send Creative Object private fields to remote models.

These constraints are part of the product architecture, not temporary implementation limitations.
